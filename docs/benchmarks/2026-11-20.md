# Benchmarks - 2026-11-20

## Environment

| Item | Value |
|---|---|
| Host | Windows 11, x86_64 |
| Emulator | QEMU 11.1.0 |
| Acceleration | TCG (no KVM/WHPX used for these runs) |
| Machine | q35, 1 vCPU (`-cpu max`), 512 MiB RAM |
| Firmware | OVMF `edk2-stable202605-r1` (rust-osdev prebuilt) |
| Display | std VGA, GOP 1280x800, 32 bpp |
| Disk | 512 MiB GPT image, FAT32 ESP, IDE |
| Build | release, Rust 1.100.0, `opt-level=2`, LTO off, debug info on |
| Date | 2026-11-20 |

These numbers are from emulated hardware with a software CPU. They are useful
for regression tracking, not for comparing Aster OS with Windows, macOS, or
Linux on real hardware.

## Method

`python tools/bench.py` starts QEMU, timestamps the appearance of serial
markers, waits for the desktop to render, then quits. Boot times are wall-clock
from QEMU launch. Frame time is reported by the desktop itself:

```
[user] desktop: frame N at <kernel ms>, <ms this frame>, <avg> ms avg
```

The desktop logs every 60 frames. The steady-state figure below is from a run
of at least 60 frames after the first frame.

## Interpretation

- Firmware time dominates boot: OVMF takes ~1.5 s under TCG before the loader
  runs. Replacing OVMF with a minimal loader or using KVM would change this
  dramatically; neither is a property of Aster OS itself.
- Serial markers are polled every 20 ms. `KERNEL-ENTRY-OK` and `KERNEL-READY`
  appear in the same polling interval, so this method does not resolve the
  kernel's init time at millisecond precision. The in-guest tick counter only
  starts when interrupts are enabled at `KERNEL-READY`; the desktop's
  "frame 1 at 1799 ms" is therefore measured **from KERNEL-READY**, not from
  kernel entry.
- The guest's PIT tick count is not a wall clock under TCG: the desktop's
  2453 ms of in-guest time corresponds to roughly 3.2 s of wall time between
  `KERNEL-READY` and `DESKTOP-READY`. Emulation overhead and delayed timer
  interrupts compress guest time relative to wall time. Do not compare guest
  tick durations with wall-clock stopwatch values.
- Kernel entry to ready measured 25 ms by the wall-clock serial poll. That is
  at the 20 ms polling resolution; the true value may be a few milliseconds
  lower. A TSC-calibrated in-kernel timer is needed for a precise breakdown.
- Desktop startup (~3.2 s wall, ~2.45 s in-guest) includes eagerly mapping
  the 48 MiB heap, generating the wallpaper/blur, loading the generated icon
  textures and initialising the shell. Demand paging and lazy heap growth are
  the obvious optimisations.
- Frame time is dominated by software composition: a full 4 MiB present copy,
  glass panels sampled per pixel with fixed-point/integer math, icon texture
  scaling and text rasterisation. Per-pixel floating point was removed from
  glass and icon scaling because QEMU's soft-float made frames take hundreds of
  milliseconds. The redesigned shell idles around 52-60 ms and slows to about
  80 ms with several windows open.
- There is no damage tracking; the entire frame is recomposed even when only
  the clock changes.

## Comparison policy

Aster OS does not claim to be faster than any other operating system. Any
future comparison must use the same host, same emulator/acceleration, same
resolution, and the same workload, and must publish raw logs. To compare with a
native OS, both systems must run on the same physical hardware with equivalent
drivers and services; that is not possible for this preview.

## Future measurements

- Scheduler latency (wake-up to user instruction) under load.
- Syscall round-trip cost for each implemented call.
- Ramfs throughput and metadata operations.
- Input-to-photon latency for typing and pointer motion.
- Boot time with KVM, with damage tracking, and with lazy heap mapping.
- Five-run medians with variance, not single samples.

## 0.2.0 M1 re-measurement

Measured after the storage stack and kernel hardening landed (QEMU TCG, one
vCPU, 512 MiB, 1280x800, boot disk plus 512 MiB data disk):

| Metric | Value |
|---|---|
| OVMF to Aster Boot | 1.457 s |
| Kernel loaded, ExitBootServices | 1.661 s |
| Kernel initialised | 1.686 s |
| Desktop initialised | 4.538 s |
| First compositor frame | 4.686 s |
| In-guest time to first frame | 2150 ms |
| Free RAM after desktop | 398 MiB of 510 MiB |
| Kernel heap | 2048 KiB mapped (after the 1 MiB self-test) |

The AHCI probe, GPT parse, FAT mount and FAT read/write self-test run inside the
1.686 s kernel initialisation window and add no visible boot delay. Frame time
is unchanged within run-to-run variance.
